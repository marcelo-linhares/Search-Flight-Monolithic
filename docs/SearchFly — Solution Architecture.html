Solution Architecture — Macro View
Node.js monolith · 8 bounded contexts · in-process EventEmitter bus
Implementation Sequence — derived from event storm
Phase 1 · Foundation
Watch Mgmt · Billing · Ledger
Stand up the credit lifecycle before anything fires. User creates a watch → Billing handles the Stripe payment → Ledger records the balance. Implement BalanceVersion optimistic lock for concurrent debit safety and the WatchSuspendedDueToCredits / WatchReactivated reactivation flow from the start.
Phase 2 · Execution
Scheduler · Integration · Search
Wire the autonomous search loop. node-cron fires SearchJob → Ledger authorises the spend (reservation) → Search calls Integration's FlightPort → results come back as FlightResultFetched. Add boot catch-up so missed cron ticks recover on restart.
Phase 3 · Intelligence
Pricing · Notification
Add the value layer. Pricing compares snapshots and emits PriceDropDetected. Notification receives it and fires AlertSent via email or push. Also fires WatchSuspendedDueToCredits alert when the Ledger signals credit exhaustion — the user-facing payoff of Phase 1.
Cross-cutting concerns
🛡️
safeListener(handler)
Wraps every async EventEmitter subscriber so an unhandled promise rejection in one BC doesn't crash the process or silently swallow the error. Applied at every bus.on(...) registration.
🔒
BalanceVersion optimistic lock
Prevents double-spend on concurrent search jobs. The Ledger appends BalanceVersion to every debit and uses a SQL WHERE version = $v check before committing a reservation.
⏰
Scheduler boot catch-up
On every process start, the Scheduler queries all active watches whose next-run timestamp is in the past and fires them immediately — ensures no watch silently skips a cycle after a deploy or crash.
🗄️
Shared DB, BC-namespaced tables
All BCs hit the same Postgres instance (monolith convenience), but each owns its table namespace — ledger.*, watch.*, billing.* etc. No cross-BC joins; integration via events only.
